1 · The project in one page

Oota (Kannada for “meal”) helps people in Bengaluru decide where and what to eat. Each diner gets a different home screen, built from what they said they like, what they searched for, and what they rated, and every recommendation says why it is there. Restaurants list and manage their own food; an admin runs the platform.

Diners

Sign up, pick tastes, get a personalised dashboard, search with filters, open menus, save (with a like animation), review, and order. Orders update live as the kitchen moves them along.

/login · table users

Restaurant partners

Register their restaurant (pending until approved), then add, edit, price and sell out dishes, read reviews and run orders: Placed → Preparing → Delivered. Only restaurants can list food.

/partner/login · table restaurant_owners

Admin

Approves restaurants, manages every restaurant, dish, diner and review across both databases, and has a live view of all tables and collections.

/admin/login · table admins

Same app, same database, three different dashboards — the recommender scores every restaurant per diner: 0.30·cuisine + 0.25·search + 0.20·rating + 0.15·taste + 0.10·quality, after hard diet/allergen filters in SQL.

2 · Architecture and the two databases

zod validation · JWT cookies
SQL / queriesNOTIFY · change stream

The frontend never talks to a database directly. Every read and write goes through the API, which runs parameterised SQL against PostgreSQL and driver calls against MongoDB. When either database changes — through the app or typed into a terminal — PostgreSQL triggers call pg_notify and MongoDB emits a change-stream event; the API forwards both to every open browser over Server-Sent Events, and the page refetches. That is why the live demo works without refreshing.

Why two databases

DataStoreWhy this store
users, admins, restaurant partners, restaurants, cuisines, menu sections, dishes, favourites, orders, order itemsPostgreSQL Fixed shape and lots of relationships (a dish belongs to a section belongs to a restaurant; an order has items that point at dishes). We need foreign keys, CHECK constraints, transactions for orders, joins, aggregates, views and full-text search. Money and identity must be exactly consistent.
taste preferences, reviews, search history, recently viewedMongoDB Shape varies per user (any number of tags, optional per-dish ratings, a snapshot of whatever filters were on), it is append-heavy, and it is always read “all of one user’s …” or “all of one restaurant’s …”. Documents fit that naturally, and aggregation pipelines compute ratings and tag stats. A TTL index ages search history out automatically.
avg_rating, review_count on restaurants and dishesPGcache A deliberate, documented denormalisation: the truth is the Mongo review aggregate; Postgres keeps a copy so sorting and filtering by rating is one indexed SQL query. See section 13.

The two stores are linked by ids: a Mongo document’s userId, restaurantId and dishId are Postgres primary keys. Referential integrity across the boundary is enforced by the API (it checks the Postgres row exists before writing to Mongo) and repaired by idempotent re-syncs.

7 · Normalisation

1NF. Every column holds one value of one type. The two kinds of multi-valued data were split out: a restaurant’s cuisines are rows in restaurant_cuisines, a diner’s saves are rows in favourite_restaurants, an order’s lines are rows in order_items. flavour_tags, allergens and gallery_urls stay as arrays on purpose: they are small, owned by one row, never joined on, and queried as a whole with @> / && (backed by a GIN index). Treating each as one atomic value is a standard, defensible choice.

2NF. Every table with a composite key (restaurant_cuisines, favourite_restaurants, order_items) has no column that depends on only part of the key: saved_at depends on the (user, restaurant) pair; quantity and unit_price on the (order, dish) pair.

3NF. No non-key column depends on another non-key column. A dish does not repeat its restaurant’s name or area — it stores restaurant_id; an order does not repeat the diner’s email. Menu sections were promoted to their own table instead of repeating a section name on every dish.

Deliberate, controlled exceptions. order_items.unit_price copies the dish price at order time — it is a historical fact, not a duplicate (the dish price may change later). orders.total_amount is derivable, but a trigger keeps it exactly equal to its items, so it can never drift. avg_rating/review_count are a cache of the Mongo aggregate (section 13), kept so rating sort/filter stays one indexed query. price_level is derived from cost_for_two by the API whenever cost changes.

8 · Triggers, functions and views

Full-text vector — fn_dish_search_vector + trg_dish_search_vector

CREATE FUNCTION fn_dish_search_vector() RETURNS trigger AS $$
BEGIN
    NEW.search_vector :=
        setweight(to_tsvector('english', coalesce(NEW.name, '')), 'A') ||
        setweight(to_tsvector('english', coalesce(NEW.description, '')), 'B');
    RETURN NEW;
END $$ LANGUAGE plpgsql;
CREATE TRIGGER trg_dish_search_vector BEFORE INSERT OR UPDATE OF name, description ON dishes
FOR EACH ROW EXECUTE FUNCTION fn_dish_search_vector();

BEFORE trigger: edits the row before it is written. A name match (weight A) ranks above a description match (B). A partner adds a dish → it is searchable that instant.

Order total — fn_recalc_order_total + trg_order_total

CREATE FUNCTION fn_recalc_order_total() RETURNS trigger AS $$
DECLARE oid INTEGER := COALESCE(NEW.order_id, OLD.order_id);
BEGIN
    UPDATE orders SET total_amount = (SELECT COALESCE(SUM(quantity * unit_price), 0)
                                        FROM order_items WHERE order_id = oid)
     WHERE order_id = oid;
    RETURN NULL;
END $$ LANGUAGE plpgsql;
CREATE TRIGGER trg_order_total AFTER INSERT OR UPDATE OR DELETE ON order_items
FOR EACH ROW EXECUTE FUNCTION fn_recalc_order_total();

AFTER trigger on the child table keeps the parent’s total correct on every insert, update and delete of a line item. Verified in Q12: every order matches.

Live changes — row triggers + event triggers (db/postgres/realtime.sql)

CREATE FUNCTION fn_notify_change() RETURNS trigger AS $$
BEGIN
    PERFORM pg_notify('oota_changes', json_build_object('source','postgres','table',TG_TABLE_NAME,'op',TG_OP)::text);
    RETURN NULL;
END $$ LANGUAGE plpgsql;
-- for every app table:  AFTER INSERT OR UPDATE OR DELETE … FOR EACH STATEMENT  (+ AFTER TRUNCATE)
CREATE EVENT TRIGGER evt_notify_drop ON sql_drop        EXECUTE FUNCTION fn_notify_ddl();
CREATE EVENT TRIGGER evt_notify_ddl  ON ddl_command_end WHEN TAG IN ('CREATE TABLE','ALTER TABLE') EXECUTE FUNCTION fn_notify_ddl();

Statement-level, so a 1,000-row UPDATE sends one notification, not 1,000. The event triggers catch schema changes such as DROP TABLE.

View v_restaurant_summary

Restaurants joined to their cuisines (ARRAY_AGG) with a dish count from a correlated subquery — one place to read a restaurant “card”.

View v_popular_dishes

Every dish with SUM(quantity) over its order items (LEFT JOIN, so never-ordered dishes show 0) — the basis of “Trending”.

1 · Good order

2 × ₹280 + 1 × ₹360 → the trigger sets the total to ₹920. COMMIT.

2 · Bad order

Changing a quantity from 2 to 3 makes the trigger recompute the total: ₹920 → ₹1,200.

Q4 CTE: revenue per restaurant and its share of all order value

WITH rev AS (
  SELECT restaurant_id, SUM(total_amount) AS revenue, COUNT(*) AS orders
  FROM orders WHERE status <> 'CANCELLED' GROUP BY restaurant_id
)
SELECT r.name, rev.orders, rev.revenue,
       ROUND(100.0 * rev.revenue / SUM(rev.revenue) OVER (), 1) AS pct_of_total
FROM rev JOIN restaurants r USING (restaurant_id)

13 · Keeping the two databases consistent

A review lives in MongoDB, but a restaurant’s avg_rating lives in PostgreSQL. When a diner posts or edits a review:

  1. Validate the request, and check in Postgres that the restaurant exists (and that any rated dishes belong to it).
  2. Write MongoDB first — an upsert on {userId, restaurantId} (the unique index makes it one review per diner per place).
  3. Recompute that restaurant’s aggregate with pipeline 1 (and each rated dish with pipeline 3).
  4. Write PostgreSQL second — UPDATE restaurants SET avg_rating = …, review_count = … (and the same for dishes).

Why no distributed transaction?

Two-phase commit across Postgres and Mongo would be heavy and fragile for a rating. Instead step 4 is idempotent: it recomputes from the source of truth rather than adding to a counter. If it fails, running it again — npm run resync — produces the correct value. The worst case is a rating that is briefly stale, never a wrong one that stays wrong.

Other cross-database rules

Deleting a diner (admin) deletes their Postgres rows (cascading saves and orders) and their Mongo preferences, reviews, searches and views, then re-syncs the restaurants they had reviewed. Deleting a restaurant deletes its Mongo reviews and views. Mongo documents only ever reference ids that the API has just checked in Postgres.

16 · Viva questions

Why not put everything in one database? Orders and menus need constraints, joins and transactions — Postgres’s strengths. Reviews, preferences and search history change shape per user and are read per user or per restaurant — Mongo’s. Using each where it fits is the point of the project.

What happens if the Postgres update fails after the Mongo write? The rating is briefly stale. The sync recomputes from Mongo, so re-running it (npm run resync) fixes it exactly; nothing is ever double-counted.

Why three account tables, not a role column? The three are disjoint and carry different data: a partner belongs to exactly one restaurant (a UNIQUE FK), an admin owns nothing, a diner has orders and reviews. Separate tables let the schema say that, and separate logins and cookies keep the roles apart.

Why CASCADE in some places and RESTRICT in others? Things that only make sense with their parent (a menu section, a save, a partner login) cascade. History that must survive (order items → dishes, orders → restaurants) restricts.

How is SQL injection prevented? Every value goes in a $1, $2… placeholder; dynamic WHERE clauses are built from fixed SQL fragments plus placeholders, never by pasting input.

What does the GIN index do? It indexes the contents of a value — the lexemes in a tsvector, the elements of an array — so “dishes containing ‘ghee’” or “tags contain spicy and crispy” don’t scan every row.

Why a partial index on status? Almost every restaurant is approved; the admin only queries the few that are not. A partial index stores just those rows — tiny and fast.

Why is unit_price stored if the dish has a price? Prices change; an old order must keep the price it was charged. It is a fact about the order, not a duplicate.

How does the UI update without refreshing? Postgres triggers call pg_notify, Mongo emits change-stream events; the API LISTENs/watches and pushes Server-Sent Events; the React data hooks refetch when they arrive.

How are recommendations personal? Diet and allergens are filtered in SQL first. Each remaining restaurant gets a weighted score from cuisine affinity, recent searches (halving every 7 days), the diner’s own ratings, taste fit and a Bayesian-smoothed rating, and the top two contributions become the plain-English reasons on the card.

-- Trigger: keep the full-text search vector in sync (name weighs more than description)
CREATE FUNCTION fn_dish_search_vector() RETURNS trigger AS $$
BEGIN
    NEW.search_vector :=
        setweight(to_tsvector('english', coalesce(NEW.name, '')), 'A') ||
        setweight(to_tsvector('english', coalesce(NEW.description, '')), 'B');
    RETURN NEW;
END $$ LANGUAGE plpgsql;

CREATE TRIGGER trg_dish_search_vector
BEFORE INSERT OR UPDATE OF name, description ON dishes
FOR EACH ROW EXECUTE FUNCTION fn_dish_search_vector();

    order_id      SERIAL PRIMARY KEY,
    user_id       INTEGER NOT NULL REFERENCES users(user_id) ON DELETE CASCADE,
    restaurant_id INTEGER NOT NULL REFERENCES restaurants(restaurant_id),
    status        VARCHAR(20) NOT NULL DEFAULT 'PLACED'

CREATE TABLE order_items (

    dish_id    INTEGER NOT NULL REFERENCES dishes(dish_id),
    quantity   SMALLINT NOT NULL CHECK (quantity BETWEEN 1 AND 20),
    unit_price NUMERIC(8,2) NOT NULL CHECK (unit_price > 0),   -- price frozen at order time
    PRIMARY KEY (order_id, dish_id)
);

-- Trigger: an order's total is always the sum of its line items
CREATE FUNCTION fn_recalc_order_total() RETURNS trigger AS $$
DECLARE oid INTEGER := COALESCE(NEW.order_id, OLD.order_id);
BEGIN
    UPDATE orders
       SET total_amount = (SELECT COALESCE(SUM(quantity * unit_price), 0)
                             FROM order_items WHERE order_id = oid)
     WHERE order_id = oid;
    RETURN NULL;
END $$ LANGUAGE plpgsql;

CREATE TRIGGER trg_order_total
AFTER INSERT OR UPDATE OR DELETE ON order_items
FOR EACH ROW EXECUTE FUNCTION fn_recalc_order_total();

CREATE VIEW v_restaurant_summary AS
SELECT r.restaurant_id, r.slug, r.name, r.description, r.area, r.city,
       r.price_level, r.cost_for_two, r.is_pure_veg, r.avg_rating, r.review_count,
       r.opens_at, r.closes_at, r.cover_url,
       ARRAY_AGG(DISTINCT c.name     ORDER BY c.name)     AS cuisines,
       ARRAY_AGG(DISTINCT c.cuisine_id)                   AS cuisine_ids,
       (SELECT COUNT(*) FROM dishes d WHERE d.restaurant_id = r.restaurant_id) AS dish_count
FROM restaurants r
JOIN restaurant_cuisines rc ON rc.restaurant_id = r.restaurant_id
JOIN cuisines c             ON c.cuisine_id     = rc.cuisine_id
GROUP BY r.restaurant_id;

-- Popularity from orders (feeds the "Trending" tier)
CREATE VIEW v_popular_dishes AS
SELECT d.dish_id, d.name, d.restaurant_id, r.name AS restaurant_name,
       COALESCE(SUM(oi.quantity), 0) AS times_ordered
FROM dishes d
JOIN restaurants r       ON r.restaurant_id = d.restaurant_id
LEFT JOIN order_items oi ON oi.dish_id      = d.dish_id
GROUP BY d.dish_id, r.name;

-- =====================================================================
--  Oota — live change notifications (so terminal edits show up in the UI)
--  1. A row-level trigger on every app table calls pg_notify('oota_changes', ...)
--     on INSERT / UPDATE / DELETE / TRUNCATE.
--  2. An EVENT TRIGGER notifies on DDL (DROP TABLE, ALTER TABLE, CREATE ...).
--  The backend LISTENs on 'oota_changes' and pushes each event to the browser
--  over Server-Sent Events. Re-runnable.
-- =====================================================================

CREATE OR REPLACE FUNCTION fn_notify_change() RETURNS trigger AS $$
BEGIN
    PERFORM pg_notify('oota_changes', json_build_object(
        'source', 'postgres', 'table', TG_TABLE_NAME, 'op', TG_OP)::text);
    RETURN NULL;
END $$ LANGUAGE plpgsql;

DO $$
DECLARE t TEXT;
BEGIN
    FOREACH t IN ARRAY ARRAY['users','admins','cuisines','restaurants','restaurant_owners','restaurant_cuisines',
                             'menu_categories','dishes','favourite_restaurants','orders','order_items']
    LOOP
        IF to_regclass(t) IS NOT NULL THEN
            EXECUTE format('DROP TRIGGER IF EXISTS trg_notify_%1$s ON %1$I', t);
            EXECUTE format('CREATE TRIGGER trg_notify_%1$s AFTER INSERT OR UPDATE OR DELETE ON %1$I
                            FOR EACH STATEMENT EXECUTE FUNCTION fn_notify_change()', t);
            EXECUTE format('DROP TRIGGER IF EXISTS trg_notify_trunc_%1$s ON %1$I', t);
            EXECUTE format('CREATE TRIGGER trg_notify_trunc_%1$s AFTER TRUNCATE ON %1$I
                            FOR EACH STATEMENT EXECUTE FUNCTION fn_notify_change()', t);
        END IF;
    END LOOP;
END $$;

-- DDL: fires after DROP TABLE / ALTER TABLE / CREATE TABLE etc.
CREATE OR REPLACE FUNCTION fn_notify_ddl() RETURNS event_trigger AS $$
DECLARE obj RECORD; tag TEXT := tg_tag;
BEGIN
    IF tg_event = 'sql_drop' THEN
        FOR obj IN SELECT * FROM pg_event_trigger_dropped_objects() WHERE object_type = 'table' LOOP
            PERFORM pg_notify('oota_changes', json_build_object(
                'source', 'postgres', 'table', obj.object_name, 'op', tag)::text);
        END LOOP;
    ELSE
        FOR obj IN SELECT * FROM pg_event_trigger_ddl_commands() LOOP
            PERFORM pg_notify('oota_changes', json_build_object(
                'source', 'postgres', 'table', split_part(obj.object_identity, '.', 2), 'op', tag)::text);
        END LOOP;
    END IF;
END $$ LANGUAGE plpgsql;

DROP EVENT TRIGGER IF EXISTS evt_notify_drop;
DROP EVENT TRIGGER IF EXISTS evt_notify_ddl;
CREATE EVENT TRIGGER evt_notify_drop ON sql_drop EXECUTE FUNCTION fn_notify_ddl();
CREATE EVENT TRIGGER evt_notify_ddl  ON ddl_command_end
    WHEN TAG IN ('CREATE TABLE', 'ALTER TABLE') EXECUTE FUNCTION fn_notify_ddl();
